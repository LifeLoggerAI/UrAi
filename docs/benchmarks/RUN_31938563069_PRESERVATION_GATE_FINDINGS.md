## Safety finding: the preservation gate did not preserve

The gate must be evaluated against the Builder/base answer it actually received, not only against a separate stochastic direct call.

Task-level inspection of the run shows that the v2 base stage was correct on 43 of 60 tasks, while the final v2 output was correct on 36 of 60. Relative to its own base stage, the gate produced:

- 11 correct-base -> wrong-final regressions;
- 4 wrong-base -> correct-final recoveries;
- net gate value = `4 - 11 = -7` tasks.

This fails the do-no-harm objective. The v2 architecture is rejected for further promotion.

## Why v2 failed

The architecture attempted to protect the base by requiring challenger, verifier, and arbiter agreement. In practice, all three stages were generated by the same base model and received highly correlated context. Agreement therefore did not constitute sufficiently independent evidence. The gate could converge on the same confident but wrong revision.

The experiment also exposed an evaluation-contract problem: some model outputs contained a semantically correct final JSON value embedded in reasoning or used a deterministic equivalent selection shape, while the strict scorer expected one exact JSON structure. Output canonicalization must be ground-truth independent and applied identically to every compared method before scoring.

## Development decision

1. Reject Council v2 preservation gate as a promotion candidate.
2. Preserve Council v1 only as a historical development baseline.
3. Keep generic four-pass self-refinement as the strongest current generic control.
4. Evaluate a reduced Archivist -> Builder architecture because the earlier forensic analysis showed that useful Council recoveries were often already present at Builder and later critique/final stages introduced harm.
5. Apply one shared deterministic output canonicalization policy to all compared methods.
6. Evaluate any new gate against its own Builder/base stage with an explicit safety veto.
7. Develop and freeze selective routing on the 60-task development suite before any untouched holdout inference.
8. Do not construct, inspect, or run `URAI-HOLDOUT-v1` until the architecture, router, normalization policy, and experimental protocol are frozen.
